# Appendix A. Glossary

Every term a newcomer meets in the book, in one line, with a pointer to
the section that explains it. It lists the terms that
Chapters 1 to 16 define: operating systems, microkernels and
capabilities, Erlang and OTP, the history and goals of erXos, the
system as a whole, construction, one source for every fact, the
kernel interface on Fiasco, processes and scheduling, domains,
authority and security, memory and budgets, native programs and
pipes, files and namespaces, devices and drivers, and storage and
updates. Later chapters add their own terms. A term that two chapters explain lists
both places, and a word with two meanings has one entry for each. The
entries are in alphabetical order.

* **1:1 threading**: A threading model in which each user thread is one kernel thread. [Chapter 4, section 4.2.1](04-history.md#421-two-answers-both-tried)
* **ABI (application binary interface)**: The binary contract between a program and what it calls: call numbers, registers, status codes and the layout of every shared structure; erXos states its own in one file, `abi/erx_abi.txt`. [Chapter 4, section 4.5.4](04-history.md#454-declarative-where-it-simplifies)
* **abstraction**: A simpler idea that stands for the hardware and hides its detail, so a program written against it runs whatever disk or network card the machine has. [Chapter 1, section 1.1.2](01-operating-systems.md#112-hiding-the-hardware)
* **action (gen_statem)**: An instruction a state callback returns beside the next state: a reply to send, a timer to set or an event to postpone. [Chapter 3, section 3.4.2](03-erlang.md#342-gen_statem)
* **adapter**: The directory `otp/erts/emulator/sys/erxos/`, the only part of ERTS that includes a `liberx` header, on which ERTS's scheduler, garbage collector, loader and distribution sit. [Chapter 9, section 9.4.2](09-processes.md#942-the-inside-of-erts-on-erxos)
* **address space**: The set of virtual addresses a process can use, and what they map to. [Chapter 1, section 1.4.1](01-operating-systems.md#141-virtual-and-physical-addresses)
* **address space identifier (ASID)**: A tag on each TLB entry that lets the translations of several processes sit in the TLB together, so a context switch need not clear it. [Chapter 1, section 1.4.3](01-operating-systems.md#143-the-tlb)
* **alias**: A reference that stands in for a pid as a send target and that its owner can switch off. [Chapter 10, section 10.3.2](10-domains.md#1032-the-checks-in-order)
* **ambient authority**: Authority a program holds by being who it is, such as a UNIX process's right to open any file its user id may open, and not because it was handed the right to one particular thing. [Chapter 1, section 1.6.5](01-operating-systems.md#165-permissions-and-the-power-of-a-user); [Chapter 2, section 2.3.1](02-microkernels.md#231-authority-in-unix); [Chapter 4, section 4.3.4](04-history.md#434-eros-safe-erlang-and-zircon-authority-and-payment)
* **anchor**: An empty space, the root of a native program's tree of spaces, which the session holds. [Chapter 13, section 13.1.1](13-native-programs.md#1311-what-a-program-consists-of)
* **application (OTP)**: OTP's unit of code above processes: a set of modules and a supervision tree that start and stop together. [Chapter 3, section 3.4.3](03-erlang.md#343-supervisor-application-and-release)
* **apps budget**: The one budget below which every app's principal hangs, with its guarantee equal to its cap. [Chapter 12, section 12.1.1](12-memory.md#1211-a-budget-is-an-account)
* **arity**: The number of a function's arguments; a function is named by its name and its arity, so `area/1` and `area/2` are different functions. [Chapter 3, section 3.1.3](03-erlang.md#313-functions-clauses-and-modules)
* **atom**: A named constant of Erlang, written as a lowercase word such as `ok` or `error`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **atomic instruction**: A processor instruction that reads and changes a memory word in one step that no other core can interrupt. [Chapter 1, section 1.7.2](01-operating-systems.md#172-locks-and-atomic-instructions)
* **backend**: One implementation of `liberx`'s calls: the Fiasco backend the system runs on, or the hosted backend that runs a runtime as a host process. [Chapter 8, section 8.2.2](08-kernel-interface.md#822-two-backends-behind-one-set-of-names)
* **BAR (base address register)**: A register of a PCIe function that says how much memory its registers need and, once written, where they appear. [Chapter 15, section 15.6](15-devices.md#156-pcie)
* **barrier**: An instruction that makes the processor finish earlier memory operations before later ones. [Chapter 1, section 1.7.3](01-operating-systems.md#173-memory-ordering)
* **BEAM**: Erlang's virtual machine: the instruction set the compiler targets and the engine that runs it. [Chapter 3, section 3.5](03-erlang.md#35-the-beam-and-erts)
* **BeamAsm**: The BEAM's just-in-time compiler, which translates each instruction into native machine code when a module is loaded. [Chapter 3, section 3.5.1](03-erlang.md#351-from-source-to-running-code)
* **behaviour**: OTP's name for a pattern of process, such as `gen_server`, whose generic part OTP supplies and whose specific part the programmer writes. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **behaviour module**: The module in which OTP supplies the generic part of a behaviour. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **bell**: A lane's doorbell, bound to the consumer's group, which the producer rings. [Chapter 10, section 10.2.1](10-domains.md#1021-a-lane)
* **BIF**: A built-in function: a function written in C inside ERTS, such as `spawn/1` or `length/1`. [Chapter 3, section 3.5.4](03-erlang.md#354-bifs-nifs-and-ports)
* **binary**: An Erlang term that is a sequence of bytes, written `<<1, 2, 3>>`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **block**: The fixed-size unit in which a block device stores data, numbered from zero. [Chapter 1, section 1.6.1](01-operating-systems.md#161-block-devices)
* **block device**: A device that stores data in fixed-size blocks and offers two operations: read block n and write block n. [Chapter 1, section 1.6.1](01-operating-systems.md#161-block-devices)
* **blocked**: The state of a process or thread that waits for something other than a core, such as a disk read or a key press. [Chapter 1, section 1.3.2](01-operating-systems.md#132-running-ready-and-blocked)
* **boot information page**: The page of starting facts, such as the handle of its crash area, that a new domain reads first. [Chapter 8, section 8.3.4](08-kernel-interface.md#834-one-request-end-to-end-a-domains-crash-area)
* **boot loader**: A program that knows enough about disks and file systems to find the kernel, load it into memory and pass it some information. [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program)
* **boot value**: Which slot the firmware booted, and whether as a trial; the slot writer reads it for itself beside the record. [Chapter 16, section 16.6.2](16-storage.md#1662-the-slot-writer-decides-from-facts-it-reads)
* **boot-selection record**: The one 512-byte sector, the file `autoboot.txt` of the record partition, that holds the whole state of an update and that the firmware reads to choose a slot. [Chapter 16, section 16.6.1](16-storage.md#1661-the-boot-selection-record)
* **broken (lane)**: A pipe lane in which a reader has found an impossible position; the reader logs it once and treats the lane as a writer that has gone and been read to the end. [Chapter 13, section 13.4.3](13-native-programs.md#1343-shared-memory-a-stranger-can-write)
* **budget**: An account for the memory a domain uses. The root service keeps one record per budget, carved from its parent's, and charges each object it creates to one; ending a budget ends everything charged to it. Built as that record; the wall that refuses a charge past a limit is designed, not built. [Chapter 1, section 1.4.7](01-operating-systems.md#147-who-pays-for-memory); [Chapter 4, section 4.3.4](04-history.md#434-eros-safe-erlang-and-zircon-authority-and-payment)
* **bus**: The wiring, and the protocol on it, that joins devices to the processor. [Chapter 1, section 1.5.6](01-operating-systems.md#156-finding-the-devices)
* **by construction**: A property that holds because the wrong state cannot be expressed, not because every participant remembered a rule. [Chapter 2, section 2.4.3](02-microkernels.md#243-mistakes-that-cannot-be-written)
* **C library**: The library that gives programs `printf`, `malloc` and `open`. [Chapter 1, section 1.1.4](01-operating-systems.md#114-the-parts-of-an-operating-system)
* **cache**: A small, fast memory close to the cores that holds recently used data. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **cache line**: The aligned block of a few dozen bytes, 64 on many current processors, in which a cache holds memory. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **cache-coherent**: A device is cache-coherent when the same hardware covers it, so its DMA reads see data still in the cache and its writes update or discard stale cached copies. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **call (IPC)**: The usual IPC pattern: a client sends a request and waits for the server's reply. [Chapter 2, section 2.2.1](02-microkernels.md#221-messages-between-address-spaces)
* **callback module**: The module a programmer writes for a behaviour, exporting the functions the behaviour calls at each step. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **cap (budget)**: The most pages a budget may spend; the root service records it, and refusing a charge past it is designed, not built. [Chapter 12, section 12.1.1](12-memory.md#1211-a-budget-is-an-account)
* **capability**: A reference to an object that the kernel honors and no program can forge, together with the rights to use it. [Chapter 2](02-microkernels.md); [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **capability table**: An array in kernel memory, one per address space, with one slot per capability. [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **Capsicum**: A system that brings capabilities to FreeBSD without changing its kernel's structure. [Chapter 2, section 2.3.6](02-microkernels.md#236-capability-systems-in-practice)
* **cause (pause)**: In the design, the reason the session keeps for each pause of a program, `job` or `signal`; the program runs only when no cause remains. Designed, not built. [Chapter 13, section 13.6.3](13-native-programs.md#1363-ctrl-c-and-the-sessions-job-control)
* **CBMC**: A model checker for C, which checks the budget arithmetic and other C cores for every input within stated bounds. [Chapter 6, section 6.5](06-construction.md#65-what-construction-cannot-say)
* **channel**: The pair of lanes between a native program and its handler, the program's only way to ask for anything. [Chapter 5, section 5.2.5](05-overview.md#525-programs-in-sub-spaces)
* **checkpoint (F2FS)**: A commit of F2FS's state that names the tables saying which blocks are in use. [Chapter 16, section 16.4.1](16-storage.md#1641-the-durable-view-is-never-overwritten)
* **child budget**: A budget the domain library carves from a domain's outer budget for each connection, which pays for the ring the domain reads and its doorbell. [Chapter 12, section 12.2](12-memory.md#122-own-and-outer-budgets)
* **child specification**: The description of one child of a supervisor: the function that starts it and its restart type. [Chapter 3, section 3.3.4](03-erlang.md#334-supervisors)
* **child (supervisor)**: A process that a supervisor starts and restarts. [Chapter 3, section 3.3.4](03-erlang.md#334-supervisors)
* **clause**: One alternative of an Erlang function: a pattern and a body. [Chapter 3, section 3.1.3](03-erlang.md#313-functions-clauses-and-modules)
* **cleaning (cache)**: Writing the dirty lines of a buffer back to memory before a device reads it. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **client**: A program that calls a server. [Chapter 2, section 2.1.2](02-microkernels.md#212-what-a-microkernel-leaves-out)
* **C-list**: A list of capabilities that a computation holds; it names an object by the position of an entry in its own list (Dennis and Van Horn's term). [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **CMSIS-SVD**: Arm's XML format in which chip vendors describe their devices' registers; erXos generates its register accessors from it. [Chapter 7, section 7.4](07-one-source.md#74-the-hardware-has-one-source-too)
* **code service**: The system domain's service that loads modules into its runtime by hash, checking each file's bytes against its SHA-256 before ERTS's loader reads them. [Chapter 9, section 9.5.2](09-processes.md#952-code-by-hash)
* **coherent (flag)**: The device-tree fact, from a node's `dma-coherent` property, that a device sees the processors' caches; a device whose facts are missing gets no DMA memory. See also cache-coherent. [Chapter 15, section 15.2.2](15-devices.md#1522-facts-the-firmware-owns)
* **command server**: `erx_command_srv`, process 1 of a session, which assigns every program's id, records the program in its starter's job and spawns its handler. [Chapter 13, section 13.2.3](13-native-programs.md#1323-the-command-server)
* **complete mediation**: Saltzer and Schroeder's principle that every access to every object must be checked for authority; a capability kernel meets it by construction. [Chapter 2, section 2.4.2](02-microkernels.md#242-why-a-small-tcb-is-checkable)
* **confused deputy**: A program acting for a client that uses its own authority on an object the client named but had no right to. [Chapter 2, section 2.3.4](02-microkernels.md#234-the-confused-deputy); [Chapter 11, section 11.6.3](11-security.md#1163-why-a-process-and-not-a-list)
* **connection**: The pair of lanes, one each way, between two domains; the only way two domains exchange messages. [Chapter 5, section 5.1.2](05-overview.md#512-domain)
* **connection agent**: `erx_connections`, the Erlang process in each domain that maps a new connection's two sides and opens a lane port for it. [Chapter 10, section 10.2.3](10-domains.md#1023-who-makes-a-connection)
* **consumer (lane)**: The domain that reads a lane's ring and alone writes its reader page. [Chapter 10, section 10.2.1](10-domains.md#1021-a-lane)
* **context switch**: Moving a core from one process or thread to another. [Chapter 1, section 1.3.3](01-operating-systems.md#133-the-context-switch)
* **contiguous memory object**: A memory object whose pages are physically contiguous, inside the range a device can reach, used for the device's rings and buffers. [Chapter 8, section 8.7.2](08-kernel-interface.md#872-devices)
* **contiguous pool**: One physically contiguous run of RAM that the root service takes at boot, outside its window, and from which it makes each device's memory. [Chapter 12, section 12.3](12-memory.md#123-the-pool)
* **cookie**: A secret atom that two Erlang nodes must share before they connect. [Chapter 3, section 3.6.2](03-erlang.md#362-nodes)
* **cooperative scheduling**: Scheduling in which a thread runs until it gives up the processor itself, by blocking or by calling a yield function. [Chapter 1, section 1.3.5](01-operating-systems.md#135-scheduling)
* **copy-on-write**: A technique in which a copy of memory shares the original's pages until either side writes one, which makes `fork` cheap. [Chapter 1, section 1.4.6](01-operating-systems.md#146-what-faults-make-possible); [Chapter 16, section 16.3](16-storage.md#163-littlefs-in-the-storage-domain)
* **core**: One of the complete processors on a chip; each core runs one stream of instructions at a time. [Chapter 1, section 1.3](01-operating-systems.md#13-processes-threads-and-scheduling)
* **CPU set**: The processors a domain's threads may run on. Designed, not built. [Chapter 5, section 5.1.4](05-overview.md#514-group)
* **crash area**: A memory object, charged to a domain's outer budget, into which its runtime writes its crash dump for the system domain to read after the domain ends. [Chapter 8, section 8.3.4](08-kernel-interface.md#834-one-request-end-to-end-a-domains-crash-area)
* **creation (node)**: The number ERTS uses to tell one run of a node from the next run under the same name; a domain's creation is its domain id. [Chapter 10, section 10.1.2](10-domains.md#1012-domain-ids-and-pids)
* **credit**: The most requests a native program may have waiting for a reply on its channel: 16. [Chapter 13, section 13.2.1](13-native-programs.md#1321-the-channel)
* **critical section**: Code that touches shared data, which only one thread at a time may run. [Chapter 1, section 1.7.1](01-operating-systems.md#171-races)
* **current and old (code)**: The two versions of a module that ERTS can hold at once; a fully qualified call always goes to the current one. [Chapter 3, section 3.6.1](03-erlang.md#361-two-versions-of-a-module)
* **Datalog**: A logic language of facts and rules, from which an engine derives every fact that follows; one of the forms erXos's principles allow for a specification. [Chapter 7, section 7.10](07-one-source.md#710-where-logic-languages-fit-and-where-they-do-not)
* **deadlock**: A state in which threads wait for locks that each other holds; the usual defense is to take locks in a fixed order. [Chapter 1, section 1.7.2](01-operating-systems.md#172-locks-and-atomic-instructions)
* **delegation**: Handing authority to another program. [Chapter 2, section 2.3.5](02-microkernels.md#235-delegation-shrinking-rights-and-revocation)
* **demand paging**: Bringing a page into memory only when it is first touched, so a program starts before all of it is read. [Chapter 1, section 1.4.6](01-operating-systems.md#146-what-faults-make-possible)
* **descriptor ring**: An array in memory whose entries each describe one buffer, its address, its length and whether the device or the driver owns it. [Chapter 1, section 1.5.4](01-operating-systems.md#154-direct-memory-access)
* **device NIF**: The one module through which Erlang reaches a device's registers, buffers and interrupts; its C parses nothing the device wrote. [Chapter 5, section 5.2.4](05-overview.md#524-driver-domains)
* **device registers**: The small set of storage locations through which software controls a device. [Chapter 1, section 1.5.1](01-operating-systems.md#151-device-registers)
* **device service**: The system domain's service that sends each holder the record of each device it holds: its object handles, its name in the CMSIS-SVD sources and its device-tree path. [Chapter 15, section 15.2.1](15-devices.md#1521-units-and-holders)
* **device shim**: The device NIF's C, in `otp/erts/emulator/nifs/erxos/`: register access, interrupt binding, queues and the DMA plan with its check. [Chapter 15, section 15.1.2](15-devices.md#1512-why-drivers-are-erlang)
* **device tree**: A data structure, handed to the kernel at boot, that describes the board's memory and devices. [Chapter 1, section 1.5.6](01-operating-systems.md#156-finding-the-devices); [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program)
* **direct memory access (DMA)**: A device's reading or writing of memory without the processor doing the copy. [Chapter 1, section 1.5.4](01-operating-systems.md#154-direct-memory-access)
* **directory**: A file whose contents map names to inode numbers. [Chapter 1, section 1.6.2](01-operating-systems.md#162-files-and-directories)
* **dirty scheduler**: One of the extra threads that ERTS keeps for C calls known to take long. [Chapter 3, section 3.5.2](03-erlang.md#352-schedulers-and-reductions)
* **dispatcher**: One helper thread per task that waits in Fiasco for any IRQ object bound to the task and wakes an executor when one fires. [Chapter 8, section 8.7.1](08-kernel-interface.md#871-one-path-for-devices-and-peers)
* **disposition**: What a process does with a signal: the default action, ignore it, or run a handler function. [Chapter 13, section 13.6](13-native-programs.md#136-signals-job-control-and-freebsds-numbers)
* **DMA range**: The device-tree fact that a device sees processor address `dma_cpu + x` at bus address `dma_bus + x`, read from the `dma-ranges` properties above its node. [Chapter 15, section 15.2.2](15-devices.md#1522-facts-the-firmware-owns)
* **domain**: A protected group of Erlang processes that share one address space and one runtime; the unit the hardware protects. [Chapter 1, section 1.3.6](01-operating-systems.md#136-how-a-process-ends); [Chapter 3, section 3.9.1](03-erlang.md#391-every-erlang-process-is-an-operating-system-process)
* **domain id**: A 32-bit number the domain service gives each domain and never reuses within a boot; the system domain's is 4. [Chapter 10, section 10.1.2](10-domains.md#1012-domain-ids-and-pids)
* **domain library**: C code in `liberx` that the domain service calls to plan, build and end domains. [Chapter 5, section 5.2.2](05-overview.md#522-the-system-domain)
* **domain pid**: A process in the system domain that stands for one domain; an exit signal to it stops the domain. [Chapter 10, section 10.8.1](10-domains.md#1081-three-layers)
* **domain service**: The system domain's Erlang service that decides to create a domain, records it and calls the domain library to build it. [Chapter 5, section 5.1.2](05-overview.md#512-domain)
* **doorbell**: An IRQ object with no device behind it, which one domain rings to wake another's sleeping executors. [Chapter 5, section 5.3.4](05-overview.md#534-a-message-to-a-service-through-a-facet)
* **drain pump**: A pump that copies a native program's output out of its pipe. [Chapter 13, section 13.5](13-native-programs.md#135-a-pipeline-end-to-end)
* **drive grant**: The FAT server's right to one partition of one drive, in place of a partition window. [Chapter 16, section 16.5.1](16-storage.md#1651-fat)
* **driver**: The code that knows one kind of device: its registers, what each bit means, the order of steps and how it fails. In erXos a driver is an Erlang process under a supervisor over a thin C device shim. [Chapter 1, section 1.5.3](01-operating-systems.md#153-drivers); [Chapter 4, section 4.5.1](04-history.md#451-erlang-wherever-practical)
* **driver domain**: An Erlang domain that holds devices; its drivers are supervised Erlang processes over the device NIF. [Chapter 5, section 5.2.4](05-overview.md#524-driver-domains)
* **driver table**: The design's list of native driver code, each row naming a device and the measurement that showed Erlang too slow for it; on Fiasco it has no rows. [Chapter 15, section 15.1.2](15-devices.md#1512-why-drivers-are-erlang)
* **driver-control facet**: The facet through which the system domain stops, starts or restarts a domain's drivers. [Chapter 15, section 15.1](15-devices.md#151-a-driver-is-a-process)
* **durable view**: What an F2FS mount rebuilds after a power cut, the last checkpoint and its chain of roll-forward records; no write ever lands on a block it references. [Chapter 16, section 16.4.1](16-storage.md#1641-the-durable-view-is-never-overwritten)
* **dynamically linked**: Said of a program that names shared libraries for the loader to map beside it. [Chapter 13, section 13.1](13-native-programs.md#131-a-program-is-a-port)
* **economy of mechanism**: Saltzer and Schroeder's principle that a design should be as small and simple as possible. [Chapter 2, section 2.4.2](02-microkernels.md#242-why-a-small-tcb-is-checkable)
* **elastic (budget)**: A budget whose cap is above its guarantee, which past its guarantee may spend what its ancestors have promised to no one. [Chapter 12, section 12.1.1](12-memory.md#1211-a-budget-is-an-account)
* **endpoint**: A kernel object between clients and the server threads that serve them; the destination of an IPC. [Chapter 2, section 2.2.1](02-microkernels.md#221-messages-between-address-spaces)
* **entry (of a kernel)**: One of the few ways a kernel is entered: at boot, on a system call or fault, and on an interrupt. [Chapter 6, section 6.7.1](06-construction.md#671-the-stack-proof)
* **enumerator**: The one process of the PCIe domain: it walks the bus, places each function's BARs inside the bridge's windows and reports each function to the device service. [Chapter 15, section 15.6.1](15-devices.md#1561-the-pcie-domain)
* **epmd**: The Erlang Port Mapper Daemon, which maps node names to the TCP ports their nodes listen on. [Chapter 3, section 3.6.2](03-erlang.md#362-nodes)
* **epoch**: A counter that every wakeup of a group advances; an executor reads it before it looks for work, and its park returns at once if it has moved, so no wakeup is lost. [Chapter 9](09-processes.md)
* **erase unit**: The large region of flash that must be erased before pages in it can be written again. [Chapter 16](16-storage.md)
* **Erlang domain**: A domain that runs one ERTS and the Erlang code of one purpose, such as a session or an app. [Chapter 5, section 5.2.3](05-overview.md#523-erlang-domains)
* **ERTS**: The Erlang Run-Time System: the whole program around the BEAM. [Chapter 3, section 3.5](03-erlang.md#35-the-beam-and-erts)
* **ERX_ESTALE**: The error a handle answers once its object has been destroyed: the generation its entry recorded no longer matches the object record's. [Chapter 2, section 2.5.4](02-microkernels.md#254-why-erxos-uses-fiasco-and-liberx-above-it)
* **ETS table**: Erlang Term Storage: a table of tuples owned by one process. [Chapter 3, section 3.5.3](03-erlang.md#353-memory-and-garbage-collection)
* **event table**: ERTS's table from each doorbell label to what the label names: a connection sink, a port sink or a process sink. [Chapter 9, section 9.4.4](09-processes.md#944-the-event-table-readiness-without-file-descriptors)
* **exception (Erlang)**: What the runtime raises when no clause matches or an operation fails; it stops the function. [Chapter 3, section 3.1.5](03-erlang.md#315-when-nothing-matches)
* **exception levels**: AArch64's name for the processor's privilege modes, numbered 0 to 3, where a higher number has more power. [Chapter 1, section 1.2.5](01-operating-systems.md#125-the-modes-on-aarch64)
* **exception (processor)**: A trap caused by the instruction the program was running, such as a page fault. [Chapter 1, section 1.2.1](01-operating-systems.md#121-three-ways-into-the-kernel)

* **slot (update)**: A pair of partitions, a boot partition and a system partition; there are two, A and B, and an update writes the one that is not running. A different sense from a group's slot. [Chapter 16, section 16.1.1](16-storage.md#1611-the-medium-and-its-partitions)
* **slot writer**: The one small domain that holds the only writable windows on the slots and the record, and decides each write from the record and the boot value; designed. [Chapter 16, section 16.6.2](16-storage.md#1662-the-slot-writer-decides-from-facts-it-reads)
* **socket**: A two-way channel between processes on one machine or on two machines across a network. [Chapter 1, section 1.7.4](01-operating-systems.md#174-talking-without-sharing)
* **space**: The kernel's name for an address space. [Chapter 1, section 1.4.7](01-operating-systems.md#147-who-pays-for-memory)
* **space bank**: EROS's account of memory, from which a program pays for every object it creates; deleting the bank frees everything paid from it. [Chapter 2, section 2.3.6](02-microkernels.md#236-capability-systems-in-practice); [Chapter 4, section 4.3.4](04-history.md#434-eros-safe-erlang-and-zircon-authority-and-payment)
* **spare**: The slot an update writes, other than the one that runs. [Chapter 16, section 16.6](16-storage.md#166-updates-through-two-slots)
* **SPIN**: A system that linked extensions written in a safe language into the kernel. [Chapter 4, section 4.3](04-history.md#43-the-lineage)
* **split ring**: Virtio's way of moving data: a descriptor table, an available ring of descriptors handed to the device and a used ring of those it has finished. [Chapter 15, section 15.3](15-devices.md#153-the-device-nif)
* **stack pointer**: The register that marks the top of a process's stack. [Chapter 1, section 1.3.1](01-operating-systems.md#131-programs-and-processes)
* **stamp**: The monotonic clock's reading that a pipe record carries, by which a reader merges several writers' lanes. [Chapter 13, section 13.4.2](13-native-programs.md#1342-one-ring-per-writer)
* **starter**: The Erlang process that asked for a native program to run; what it handed over bounds the program's table. [Chapter 13](13-native-programs.md)
* **startup message**: What the handler writes into a new program's inbound lane before its first thread starts: arguments, environment, working directory, signal state and descriptors. [Chapter 13, section 13.3.1](13-native-programs.md#1331-from-the-shells-line-to-main)
* **starvation**: The failure in which a low-priority thread never runs because higher ones are always ready. [Chapter 1, section 1.3.5](01-operating-systems.md#135-scheduling)
* **statically linked**: Said of a program that carries every library function it calls in its own file. [Chapter 13, section 13.1](13-native-programs.md#131-a-program-is-a-port)
* **store-release**: A store the processor may not make visible before the stores ahead of it. [Chapter 13, section 13.4.5](13-native-programs.md#1345-doorbells-and-lost-wakeups)
* **stream file**: A file whose reads wait for an event, answered by a keeper instead of by the file server's callback. [Chapter 14, section 14.2.5](14-files.md#1425-stream-files-and-keepers)
* **sub-space**: An address space a domain creates for a native program; it holds only what the domain gives it and ends with its creator. [Chapter 5, section 5.2.5](05-overview.md#525-programs-in-sub-spaces)
* **supervisor**: A process whose only job is to start other processes, its children, and to restart them when they stop. [Chapter 3, section 3.3.4](03-erlang.md#334-supervisors)
* **synchronous (IPC)**: Moving a message only when the sender is ready to send and the receiver is ready to receive. [Chapter 2, section 2.2.1](02-microkernels.md#221-messages-between-address-spaces)
* **system call**: A deliberate request from a program to the kernel. [Chapter 1, section 1.2.1](01-operating-systems.md#121-three-ways-into-the-kernel)
* **system domain**: The Erlang domain that decides policy and builds every other domain; it is erXos's root task. [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program); [Chapter 2, section 2.5.3](02-microkernels.md#253-the-root-task); [Chapter 3, section 3.9.1](03-erlang.md#391-every-erlang-process-is-an-operating-system-process)
* **system knowledge base**: Barrelfish's store of facts about the hardware, in a subset of first-order logic, which answered queries such as where a driver should run. [Chapter 7, section 7.10](07-one-source.md#710-where-logic-languages-fit-and-where-they-do-not)
* **system manifest**: The one file that names every domain the machine runs, with its budget, its devices and the services it may reach. [Chapter 4, section 4.5.4](04-history.md#454-declarative-where-it-simplifies)
* **`system` tree**: The `apps/` directory of the booted slot's system partition, served read-only by the storage domain through `erx_storage_system`. [Chapter 16, section 16.2.3](16-storage.md#1623-the-system-tree-and-every-reader-checks-for-itself)
* **table (program)**: What a native program may reach, its namespace, open files and pipe ends, kept by its handler. [Chapter 13, section 13.1.1](13-native-programs.md#1311-what-a-program-consists-of)
* **tail call**: A recursive call that is the last thing a function does; the runtime turns it into a jump that uses no stack. [Chapter 3, section 3.1.4](03-erlang.md#314-recursion-in-place-of-loops)
* **task (Fiasco)**: Fiasco's name for an address space together with the kernel objects its threads may use. [Chapter 2, section 2.5.2](02-microkernels.md#252-fiasco-and-l4re)
* **term**: Any Erlang value. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **thread**: One stream of execution: a program counter, a stack and a set of registers. [Chapter 1, section 1.3.4](01-operating-systems.md#134-threads)
* **thread limit**: The cap on how many threads a domain may have. Designed, not built. [Chapter 5, section 5.1.4](05-overview.md#514-group)
* **threat model**: A statement of who a security design defends against, what each adversary can and must not be able to do, the assets it protects and what it leaves out. [Chapter 11](11-security.md)
* **time of check to time of use**: A bug in which an argument changes between the kernel's check and its use; kernels avoid it by copying each argument once and using only the copy. [Chapter 1, section 1.2.2](01-operating-systems.md#122-a-system-call-from-start-to-finish)
* **time slice**: The few milliseconds a thread runs before the timer interrupt lets the kernel choose again. [Chapter 1, section 1.3.5](01-operating-systems.md#135-scheduling)
* **timer interrupt**: The interrupt by which a timer takes the processor back from the running program. [Chapter 1, section 1.2.3](01-operating-systems.md#123-the-timer-and-taking-the-processor-back)
* **TLA+ and TLC**: Leslie Lamport's language for describing a concurrent protocol, and its model checker; erXos specifies its lane, connections and links in it. [Chapter 6, section 6.5](06-construction.md#65-what-construction-cannot-say)
* **trace ring**: 4,096 records that `liberx` writes in the root service as it carries out parks, wakes and doorbell deliveries, merged with OTP's own trace into one timeline. [Chapter 9, section 9.7.1](09-processes.md#971-one-timeline)
* **translation lookaside buffer (TLB)**: A small cache of recent address translations inside the processor. [Chapter 1, section 1.4.3](01-operating-systems.md#143-the-tlb)
* **trap**: The special instruction that switches the processor to kernel mode and jumps into the kernel. [Chapter 1, section 1.2.1](01-operating-systems.md#121-three-ways-into-the-kernel)
* **tree process**: The one Erlang process that holds the whole value of `/tmp`'s tree and answers every callback by one step of a pure function. [Chapter 14, section 14.4](14-files.md#144-tmp-a-file-system-in-erlang)
* **trial**: The one boot of the spare slot after an update; it becomes the committed slot only if the trial is healthy, and a trial writes nothing but the record. [Chapter 16, section 16.6](16-storage.md#166-updates-through-two-slots)
* **trust placement**: For each security property, the short list of code it rests on. [Chapter 11, section 11.2.1](11-security.md#1121-two-things-keep-domains-apart)
* **trusted base**: erXos's trusted computing base: Fiasco, the root service and the rest of the system domain. [Chapter 11, section 11.2.2](11-security.md#1122-the-trusted-base)
* **trusted computing base (TCB)**: The parts of a system whose failure can break its security, as opposed to the parts whose failure harms only themselves. [Chapter 2, section 2.4.1](02-microkernels.md#241-the-trusted-computing-base)
* **tuple**: A fixed number of Erlang terms in braces: `{point, 1, 2}`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **two-level scheduling**: An arrangement in which the kernel schedules at one level and a user-mode scheduler at the other. [Chapter 4, section 4.2](04-history.md#42-thirty-years-of-two-level-scheduling)
* **umtx wait**: A wait on a memory address, from which musl builds its mutexes and condition variables. [Chapter 8, section 8.5.2](08-kernel-interface.md#852-waiting-one-semaphore-per-thread)
* **unforgeable**: A property of a capability: no program can make one by itself. [Chapter 2, section 2.3.3](02-microkernels.md#233-why-a-capability-cannot-be-forged)
* **unit (manifest)**: A set of devices that share a register page or an interrupt line, given whole to one domain. [Chapter 7, section 7.7](07-one-source.md#77-the-system-manifest-the-machines-configuration-checked)
* **upcall**: A call from the kernel into user code. [Chapter 4, section 4.2.2](04-history.md#422-the-common-failure)
* **user mode**: The processor mode that refuses privileged instructions. [Chapter 1, section 1.2](01-operating-systems.md#12-the-processors-two-modes-and-the-way-across)
* **user-level thread**: A thread a program schedules itself on top of a few kernel threads, switching with no system call; Erlang's processes are of this kind. [Chapter 1, section 1.3.4](01-operating-systems.md#134-threads)
* **UTCB**: A user thread control block: a small block of memory per thread for message words, shared by the thread and the kernel. [Chapter 2, section 2.2.2](02-microkernels.md#222-how-l4-made-ipc-fast)
* **virtio**: The standard that defines devices designed for emulation, such as a network card, a disk, a GPU and a keyboard, each with a few registers and one split ring. [Chapter 15, section 15.3](15-devices.md#153-the-device-nif)
* **virtual address**: An address a program uses, which the MMU translates to a physical address. [Chapter 1, section 1.4.1](01-operating-systems.md#141-virtual-and-physical-addresses)
* **wake word**: The counter every wait in `liberx` sleeps on; a signal's sender bumps it first, so the thread cannot sleep through the signal. [Chapter 13, section 13.6.4](13-native-programs.md#1364-signals-through-vcpu-upcalls)
* **wall (budget)**: A budget whose cap equals its guarantee: memory set aside for a domain that no other domain can take. The records are built; the refusal that makes a wall hold is designed, not built. [Chapter 12](12-memory.md); [Chapter 12, section 12.1.1](12-memory.md#1211-a-budget-is-an-account)
* **window**: The region of the root service's address space where every page of RAM has one permanent address. [Chapter 8, section 8.6.1](08-kernel-interface.md#861-one-page-one-address)
* **worker**: A process that does the work, a leaf of a supervision tree. [Chapter 3, section 3.3.5](03-erlang.md#335-supervision-trees)
* **worker (thread)**: A thread of a runtime that may block, such as ERTS's dirty I/O thread; it never parks. [Chapter 9](09-processes.md)
* **writable and executable at once**: The state of a page that a program could both rewrite and run; the rule W^X forbids it. [Chapter 1, section 1.4.4](01-operating-systems.md#144-protection-bits)
* **Zircon**: The kernel of Google's Fuchsia, which gives every process a table of handles with rights. [Chapter 2, section 2.3.6](02-microkernels.md#236-capability-systems-in-practice)
