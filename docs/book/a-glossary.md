# Appendix A. Glossary

Every term a newcomer meets in the book, in one line, with a pointer to
the section that explains it. This first version lists the terms that
Chapters 1 to 4 define: operating systems, microkernels and
capabilities, Erlang and OTP, and the history and goals of erXos. Later
chapters add their own terms. A term that two chapters explain lists
both places, and a word with two meanings has one entry for each. The
entries are in alphabetical order.

* **1:1 threading**: A threading model in which each user thread is one kernel thread. [Chapter 4, section 4.2.1](04-history.md#421-two-answers-both-tried)
* **abstraction**: A simpler idea that stands for the hardware and hides its detail, so a program written against it runs whatever disk or network card the machine has. [Chapter 1, section 1.1.2](01-operating-systems.md#112-hiding-the-hardware)
* **action (gen_statem)**: An instruction a state callback returns beside the next state: a reply to send, a timer to set or an event to postpone. [Chapter 3, section 3.4.2](03-erlang.md#342-gen_statem)
* **address space**: The set of virtual addresses a process can use, and what they map to. [Chapter 1, section 1.4.1](01-operating-systems.md#141-virtual-and-physical-addresses)
* **address space identifier (ASID)**: A tag on each TLB entry that lets the translations of several processes sit in the TLB together, so a context switch need not clear it. [Chapter 1, section 1.4.3](01-operating-systems.md#143-the-tlb)
* **ambient authority**: Authority a program holds by being who it is, such as a UNIX process's right to open any file its user id may open, and not because it was handed the right to one particular thing. [Chapter 1, section 1.6.5](01-operating-systems.md#165-permissions-and-the-power-of-a-user); [Chapter 2, section 2.3.1](02-microkernels.md#231-authority-in-unix); [Chapter 4, section 4.3.4](04-history.md#434-eros-safe-erlang-and-zircon-authority-and-payment)
* **application (OTP)**: OTP's unit of code above processes: a set of modules and a supervision tree that start and stop together. [Chapter 3, section 3.4.3](03-erlang.md#343-supervisor-application-and-release)
* **arity**: The number of a function's arguments; a function is named by its name and its arity, so `area/1` and `area/2` are different functions. [Chapter 3, section 3.1.3](03-erlang.md#313-functions-clauses-and-modules)
* **atom**: A named constant of Erlang, written as a lowercase word such as `ok` or `error`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **atomic instruction**: A processor instruction that reads and changes a memory word in one step that no other core can interrupt. [Chapter 1, section 1.7.2](01-operating-systems.md#172-locks-and-atomic-instructions)
* **barrier**: An instruction that makes the processor finish earlier memory operations before later ones. [Chapter 1, section 1.7.3](01-operating-systems.md#173-memory-ordering)
* **BEAM**: Erlang's virtual machine: the instruction set the compiler targets and the engine that runs it. [Chapter 3, section 3.5](03-erlang.md#35-the-beam-and-erts)
* **BeamAsm**: The BEAM's just-in-time compiler, which translates each instruction into native machine code when a module is loaded. [Chapter 3, section 3.5.1](03-erlang.md#351-from-source-to-running-code)
* **behaviour**: OTP's name for a pattern of process, such as `gen_server`, whose generic part OTP supplies and whose specific part the programmer writes. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **behaviour module**: The module in which OTP supplies the generic part of a behaviour. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **BIF**: A built-in function: a function written in C inside ERTS, such as `spawn/1` or `length/1`. [Chapter 3, section 3.5.4](03-erlang.md#354-bifs-nifs-and-ports)
* **binary**: An Erlang term that is a sequence of bytes, written `<<1, 2, 3>>`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **block**: The fixed-size unit in which a block device stores data, numbered from zero. [Chapter 1, section 1.6.1](01-operating-systems.md#161-block-devices)
* **block device**: A device that stores data in fixed-size blocks and offers two operations: read block n and write block n. [Chapter 1, section 1.6.1](01-operating-systems.md#161-block-devices)
* **blocked**: The state of a process or thread that waits for something other than a core, such as a disk read or a key press. [Chapter 1, section 1.3.2](01-operating-systems.md#132-running-ready-and-blocked)
* **boot loader**: A program that knows enough about disks and file systems to find the kernel, load it into memory and pass it some information. [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program)
* **budget**: A kernel object that pays for memory: every page, the kernel's own included, is charged to one, and no domain can take memory another was promised. [Chapter 1, section 1.4.7](01-operating-systems.md#147-who-pays-for-memory); [Chapter 4, section 4.3.4](04-history.md#434-eros-safe-erlang-and-zircon-authority-and-payment)
* **bus**: The wiring, and the protocol on it, that joins devices to the processor. [Chapter 1, section 1.5.6](01-operating-systems.md#156-finding-the-devices)
* **by construction**: A property that holds because the wrong state cannot be expressed, not because every participant remembered a rule. [Chapter 2, section 2.4.3](02-microkernels.md#243-mistakes-that-cannot-be-written)
* **C library**: The library that gives programs `printf`, `malloc` and `open`. [Chapter 1, section 1.1.4](01-operating-systems.md#114-the-parts-of-an-operating-system)
* **cache**: A small, fast memory close to the cores that holds recently used data. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **cache line**: The aligned block of a few dozen bytes, 64 on many current processors, in which a cache holds memory. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **cache-coherent**: A device is cache-coherent when the same hardware covers it, so its DMA reads see data still in the cache and its writes update or discard stale cached copies. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **call (IPC)**: The usual IPC pattern: a client sends a request and waits for the server's reply. [Chapter 2, section 2.2.1](02-microkernels.md#221-messages-between-address-spaces)
* **callback module**: The module a programmer writes for a behaviour, exporting the functions the behaviour calls at each step. [Chapter 3, section 3.4](03-erlang.md#34-otp-behaviours)
* **capability**: A reference to an object that the kernel honors and no program can forge, together with the rights to use it. [Chapter 2](02-microkernels.md); [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **capability table**: An array in kernel memory, one per address space, with one slot per capability. [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **Capsicum**: A system that brings capabilities to FreeBSD without changing its kernel's structure. [Chapter 2, section 2.3.6](02-microkernels.md#236-capability-systems-in-practice)
* **child specification**: The description of one child of a supervisor: the function that starts it and its restart type. [Chapter 3, section 3.3.4](03-erlang.md#334-supervisors)
* **child (supervisor)**: A process that a supervisor starts and restarts. [Chapter 3, section 3.3.4](03-erlang.md#334-supervisors)
* **clause**: One alternative of an Erlang function: a pattern and a body. [Chapter 3, section 3.1.3](03-erlang.md#313-functions-clauses-and-modules)
* **cleaning (cache)**: Writing the dirty lines of a buffer back to memory before a device reads it. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **client**: A program that calls a server. [Chapter 2, section 2.1.2](02-microkernels.md#212-what-a-microkernel-leaves-out)
* **C-list**: A list of capabilities that a computation holds; it names an object by the position of an entry in its own list (Dennis and Van Horn's term). [Chapter 2, section 2.3.2](02-microkernels.md#232-a-capability-is-a-reference-with-rights)
* **complete mediation**: Saltzer and Schroeder's principle that every access to every object must be checked for authority; a capability kernel meets it by construction. [Chapter 2, section 2.4.2](02-microkernels.md#242-why-a-small-tcb-is-checkable)
* **context switch**: Moving a core from one process or thread to another. [Chapter 1, section 1.3.3](01-operating-systems.md#133-the-context-switch)
* **cookie**: A secret atom that two Erlang nodes must share before they connect. [Chapter 3, section 3.6.2](03-erlang.md#362-nodes)
* **cooperative scheduling**: Scheduling in which a thread runs until it gives up the processor itself, by blocking or by calling a yield function. [Chapter 1, section 1.3.5](01-operating-systems.md#135-scheduling)
* **copy-on-write**: A technique in which a copy of memory shares the original's pages until either side writes one, which makes `fork` cheap. [Chapter 1, section 1.4.6](01-operating-systems.md#146-what-faults-make-possible)
* **core**: One of the complete processors on a chip; each core runs one stream of instructions at a time. [Chapter 1, section 1.3](01-operating-systems.md#13-processes-threads-and-scheduling)
* **critical section**: Code that touches shared data, which only one thread at a time may run. [Chapter 1, section 1.7.1](01-operating-systems.md#171-races)
* **current and old (code)**: The two versions of a module that ERTS can hold at once; a fully qualified call always goes to the current one. [Chapter 3, section 3.6.1](03-erlang.md#361-two-versions-of-a-module)
* **deadlock**: A state in which threads wait for locks that each other holds; the usual defense is to take locks in a fixed order. [Chapter 1, section 1.7.2](01-operating-systems.md#172-locks-and-atomic-instructions)
* **delegation**: Handing authority to another program. [Chapter 2, section 2.3.5](02-microkernels.md#235-delegation-shrinking-rights-and-revocation)
* **demand paging**: Bringing a page into memory only when it is first touched, so a program starts before all of it is read. [Chapter 1, section 1.4.6](01-operating-systems.md#146-what-faults-make-possible)
* **descriptor ring**: An array in memory whose entries each describe one buffer, its address, its length and whether the device or the driver owns it. [Chapter 1, section 1.5.4](01-operating-systems.md#154-direct-memory-access)
* **development build**: A build that runs only trusted code and prints `development build: trusted code only` on boot. [Chapter 4, section 4.6.4](04-history.md#464-the-phases)
* **device registers**: The small set of storage locations through which software controls a device. [Chapter 1, section 1.5.1](01-operating-systems.md#151-device-registers)
* **device tree**: A data structure, handed to the kernel at boot, that describes the board's memory and devices. [Chapter 1, section 1.5.6](01-operating-systems.md#156-finding-the-devices); [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program)
* **direct memory access (DMA)**: A device's reading or writing of memory without the processor doing the copy. [Chapter 1, section 1.5.4](01-operating-systems.md#154-direct-memory-access)
* **directory**: A file whose contents map names to inode numbers. [Chapter 1, section 1.6.2](01-operating-systems.md#162-files-and-directories)
* **dirty scheduler**: One of the extra threads that ERTS keeps for C calls known to take long. [Chapter 3, section 3.5.2](03-erlang.md#352-schedulers-and-reductions)
* **domain**: A protected group of Erlang processes that share one address space and one runtime; the unit the hardware protects. [Chapter 1, section 1.3.6](01-operating-systems.md#136-how-a-process-ends); [Chapter 3, section 3.9.1](03-erlang.md#391-every-erlang-process-is-an-operating-system-process)
* **driver**: The code that knows one kind of device: its registers, what each bit means, the order of steps and how it fails. In erXos a driver is an Erlang process under a supervisor over a thin C device shim. [Chapter 1, section 1.5.3](01-operating-systems.md#153-drivers); [Chapter 4, section 4.5.1](04-history.md#451-erlang-wherever-practical)
* **economy of mechanism**: Saltzer and Schroeder's principle that a design should be as small and simple as possible. [Chapter 2, section 2.4.2](02-microkernels.md#242-why-a-small-tcb-is-checkable)
* **endpoint**: A kernel object between clients and the server threads that serve them; the destination of an IPC. [Chapter 2, section 2.2.1](02-microkernels.md#221-messages-between-address-spaces)
* **epmd**: The Erlang Port Mapper Daemon, which maps node names to the TCP ports their nodes listen on. [Chapter 3, section 3.6.2](03-erlang.md#362-nodes)
* **ERTS**: The Erlang Run-Time System: the whole program around the BEAM. [Chapter 3, section 3.5](03-erlang.md#35-the-beam-and-erts)
* **ETS table**: Erlang Term Storage: a table of tuples owned by one process. [Chapter 3, section 3.5.3](03-erlang.md#353-memory-and-garbage-collection)
* **exception (Erlang)**: What the runtime raises when no clause matches or an operation fails; it stops the function. [Chapter 3, section 3.1.5](03-erlang.md#315-when-nothing-matches)
* **exception levels**: AArch64's name for the processor's privilege modes, numbered 0 to 3, where a higher number has more power. [Chapter 1, section 1.2.5](01-operating-systems.md#125-the-modes-on-aarch64)
* **exception (processor)**: A trap caused by the instruction the program was running, such as a page fault. [Chapter 1, section 1.2.1](01-operating-systems.md#121-three-ways-into-the-kernel)
* **executor**: erXos's name for a thread on which ERTS runs many processes. [Chapter 4, section 4.2.3](04-history.md#423-why-erxos-keeps-two-levels)
* **exit reason**: The term that a process's exit signal carries. [Chapter 3, section 3.3.2](03-erlang.md#332-links-and-exit-signals)
* **exit signal**: The signal the runtime sends to every process linked to one that ends, carrying its pid and exit reason; the runtime acts on it before any receive sees it. [Chapter 3, section 3.3.2](03-erlang.md#332-links-and-exit-signals)
* **exit status**: The small number a process gives to `exit`, where 0 means success. [Chapter 1, section 1.3.6](01-operating-systems.md#136-how-a-process-ends)
* **export (domain)**: To make one of a domain's processes reachable by another domain, by sending its pid or explicitly; a pid never exported names nothing. [Chapter 3, section 3.9.2](03-erlang.md#392-distribution-across-a-domains-wall)
* **export table**: A domain's own record of the processes it has exported to peer domains. [Chapter 3, section 3.9.2](03-erlang.md#392-distribution-across-a-domains-wall)
* **external term format**: The byte encoding of Erlang terms that `term_to_binary/1` produces and distribution sends. [Chapter 3, section 3.6.3](03-erlang.md#363-how-a-message-crosses-between-nodes)
* **Fiasco**: An L4 kernel from the Technische Universitaet Dresden, written almost entirely in C++; the kernel erXos runs on. [Chapter 1, section 1.1.4](01-operating-systems.md#114-the-parts-of-an-operating-system); [Chapter 2, section 2.5.2](02-microkernels.md#252-fiasco-and-l4re); [Chapter 3, section 3.9](03-erlang.md#39-how-erxos-uses-these-ideas)
* **file**: A named sequence of bytes that outlives the process that wrote it. [Chapter 1, section 1.6.2](01-operating-systems.md#162-files-and-directories)
* **file descriptor**: A small integer that names an open file in one process. [Chapter 1, section 1.6.3](01-operating-systems.md#163-file-descriptors)
* **file system**: The layout that stores files and directories on a block device. [Chapter 1, section 1.6.4](01-operating-systems.md#164-file-systems-and-mounting)
* **firmware**: Code stored in a chip on the board that runs when the power comes on. [Chapter 1, section 1.8](01-operating-systems.md#18-from-power-on-to-the-first-program)
* **flush (L4)**: The L4 operation that removes a page from every space that received it from the flusher, directly or indirectly. [Chapter 2, section 2.2.3](02-microkernels.md#223-shared-memory-beside-messages)
* **frame (distribution)**: The bytes of a message between nodes plus a small header that says what they are and between which processes. [Chapter 3, section 3.6.3](03-erlang.md#363-how-a-message-crosses-between-nodes)
* **fully qualified call**: A call written `Module:Function(Args)`, which always goes to the current version of the module. [Chapter 3, section 3.6.1](03-erlang.md#361-two-versions-of-a-module)
* **fun**: A function used as an Erlang value. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **funnel**: The one function of a domain that decodes messages arriving from another domain. [Chapter 3, section 3.9.2](03-erlang.md#392-distribution-across-a-domains-wall)
* **generation**: A counter stored with each capability slot that goes up whenever the slot is reused, so a stale capability never names a new object. [Chapter 2, section 2.3.5](02-microkernels.md#235-delegation-shrinking-rights-and-revocation)
* **grant (CPU)**: The CPU time a domain's threads may use, within which each runtime schedules its own processes; on Fiasco it is a priority band, a set of CPUs and a thread limit. [Chapter 4, section 4.2.3](04-history.md#423-why-erxos-keeps-two-levels)
* **grant (page)**: The L4 operation that gives a page to another address space; the granter loses it. [Chapter 2, section 2.2.3](02-microkernels.md#223-shared-memory-beside-messages)
* **group**: A kernel object that holds a share of CPU time; the kernel charges thread time to a group. [Chapter 1, section 1.3.6](01-operating-systems.md#136-how-a-process-ends); [Chapter 4, section 4.2.3](04-history.md#423-why-erxos-keeps-two-levels)
* **guard**: A test on bound variables, written after `when`, that a clause adds to its pattern. [Chapter 3, section 3.1.3](03-erlang.md#313-functions-clauses-and-modules)
* **HydrOS**: A system that ran one BEAM per CPU core over a small kernel, with drivers written only in Erlang. [Chapter 4, section 4.1.4](04-history.md#414-erlang-below-the-application-tried-before)
* **immutable**: Never changed after it is made; all data in Erlang is. [Chapter 3, section 3.1.2](03-erlang.md#312-variables-bind-once)
* **inode**: A record that holds a file's size, owner, permission bits and the list of blocks where its bytes lie. [Chapter 1, section 1.6.2](01-operating-systems.md#162-files-and-directories)
* **interpreter (BEAM)**: The part of ERTS that runs BEAM instructions directly, fetching and dispatching each in turn. [Chapter 3, section 3.5.1](03-erlang.md#351-from-source-to-running-code)
* **inter-process communication (IPC)**: The ways separate processes exchange data: pipes, sockets, messages and shared memory. In a microkernel, the kernel carries a message from one address space to another. [Chapter 1, section 1.7.4](01-operating-systems.md#174-talking-without-sharing); [Chapter 2, section 2.1.2](02-microkernels.md#212-what-a-microkernel-leaves-out)
* **interrupt**: A signal from outside the running program, such as a device finishing work, that makes the processor enter the kernel. [Chapter 1, section 1.2.1](01-operating-systems.md#121-three-ways-into-the-kernel)
* **interrupt controller**: The hardware that collects the interrupts of many devices, decides which core gets each, and lets the kernel mask and acknowledge them. [Chapter 1, section 1.5.2](01-operating-systems.md#152-polling-and-interrupts)
* **invalidating (cache)**: Marking the lines of a buffer stale before reading data a device wrote, so the next load fetches from memory. [Chapter 1, section 1.5.5](01-operating-systems.md#155-caches-and-devices-that-do-not-see-them)
* **IOMMU**: A translation unit between devices and memory that works like the MMU but for devices, so a device can reach only the memory it was given. [Chapter 1, section 1.5.4](01-operating-systems.md#154-direct-memory-access)
* **IPC gate**: Fiasco's endpoint: a kernel object bound to one server thread, called through a capability. [Chapter 2, section 2.5.2](02-microkernels.md#252-fiasco-and-l4re)
* **JIT**: A just-in-time compiler: a compiler that runs inside the program it serves and produces machine code while that program runs. [Chapter 3, section 3.5.1](03-erlang.md#351-from-source-to-running-code)
* **journal**: A log to which a file system writes a note of a whole change first, so that it can replay the notes after a crash. [Chapter 1, section 1.6.4](01-operating-systems.md#164-file-systems-and-mounting)
* **kernel**: The core of an operating system, which runs with the processor's full power. [Chapter 1](01-operating-systems.md)
* **kernel interface**: The calls, rights, status codes and binary layouts defined in `abi/erx_abi.txt`, which `liberx` offers to every runtime and service over Fiasco. [Chapter 4, section 4.6.1](04-history.md#461-seams)
* **kernel mode**: The processor mode in which it executes every instruction it has. [Chapter 1, section 1.2](01-operating-systems.md#12-the-processors-two-modes-and-the-way-across)
* **kernel panic**: A deliberate stop of the machine by a kernel that finds its own data inconsistent, because going on could corrupt the files on disk. [Chapter 1, section 1.9](01-operating-systems.md#19-when-a-part-fails)
* **kernel threads**: Threads that the kernel knows, saves the registers of and schedules. [Chapter 1, section 1.3.4](01-operating-systems.md#134-threads)
* **KeyKOS and EROS**: Capability systems: KeyKOS (first called GNOSIS) was built at Tymshare and first deployed in 1982, and EROS reimplemented its architecture in the 1990s. EROS space banks are the model for erXos budgets. [Chapter 2, section 2.3.6](02-microkernels.md#236-capability-systems-in-practice)
* **L4**: The family of microkernels that Liedtke began, which this book follows to Fiasco. [Chapter 2, section 2.1.4](02-microkernels.md#214-mach-qnx-minix-and-l4)
* **L4Re**: The L4 Runtime Environment: the user-mode libraries and servers that a system on Fiasco needs. [Chapter 2, section 2.5.2](02-microkernels.md#252-fiasco-and-l4re)
* **label**: A number a server chooses when it binds an IPC gate; the server learns it with each call and uses it to tell clients apart. [Chapter 2, section 2.5.2](02-microkernels.md#252-fiasco-and-l4re)
* **lane**: One direction of a connection between two domains, a ring buffer that the sender alone writes. [Chapter 1, section 1.7.4](01-operating-systems.md#174-talking-without-sharing)
* **library**: Code that programs link with and call like their own functions. [Chapter 1, section 1.1.4](01-operating-systems.md#114-the-parts-of-an-operating-system)
* **LING**: A reimplementation of the BEAM that boots with no operating system beneath it, as a guest of the Xen hypervisor. [Chapter 4, section 4.1.4](04-history.md#414-erlang-below-the-application-tried-before)
* **link (Erlang)**: A connection between two processes so that each learns when the other stops. [Chapter 3, section 3.3.2](03-erlang.md#332-links-and-exit-signals)
* **list comprehension**: An expression that builds one list from another: `[2 * X || X <- [1, 2, 3]]`. [Chapter 3, section 3.1.4](03-erlang.md#314-recursion-in-place-of-loops)
* **list (Erlang)**: A term holding any number of terms, written in brackets: `[1, 2, 3]`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **livelock**: A failure in which the processor handles interrupts and nothing else, because they arrive faster than it can serve them. [Chapter 1, section 1.5.2](01-operating-systems.md#152-polling-and-interrupts)
* **loader (ERTS)**: The part of ERTS that reads a module file when the module is first needed and prepares it to run. [Chapter 3, section 3.5.1](03-erlang.md#351-from-source-to-running-code)
* **lock**: A variable that guards a critical section; also called a mutex. [Chapter 1, section 1.7.2](01-operating-systems.md#172-locks-and-atomic-instructions)
* **Mach**: An operating-systems research project at Carnegie Mellon University, active from 1985 to 1994, whose kernel was among the first microkernels. [Chapter 2, section 2.1.4](02-microkernels.md#214-mach-qnx-minix-and-l4)
* **mailbox**: The queue of incoming messages that each Erlang process has. [Chapter 3, section 3.2.1](03-erlang.md#321-spawn-send-and-receive)
* **map (Erlang)**: A term of keys and values: `#{name => "eth0"}`. [Chapter 3, section 3.1.1](03-erlang.md#311-terms)
* **map (L4)**: The L4 operation that puts a page into another address space; the mapper keeps it. [Chapter 2, section 2.2.3](02-microkernels.md#223-shared-memory-beside-messages)
* **mapping**: The placement of part of a memory object in a space, with rights no greater than those of the capability that made it. [Chapter 1, section 1.4.7](01-operating-systems.md#147-who-pays-for-memory)
* **match**: The `=` operator of Erlang: it binds unbound variables so that the pattern equals the value, or fails. [Chapter 3, section 3.1.2](03-erlang.md#312-variables-bind-once)
* **mechanism**: The code that carries a decision out, such as stopping one program and starting another; kept apart from policy. [Chapter 1, section 1.1.1](01-operating-systems.md#111-sharing)
* **memory management unit (MMU)**: The part of the processor that translates virtual addresses to physical ones. [Chapter 1, section 1.4.1](01-operating-systems.md#141-virtual-and-physical-addresses)
* **memory model**: The rules for what reordering of memory operations a processor allows. [Chapter 1, section 1.7.3](01-operating-systems.md#173-memory-ordering)
* **memory object**: A kernel object that holds pages, which mappings place in spaces. [Chapter 1, section 1.4.7](01-operating-systems.md#147-who-pays-for-memory)
* **memory-mapped file**: A file whose contents appear in an address space. [Chapter 1, section 1.4.6](01-operating-systems.md#146-what-faults-make-possible)
* **memory-mapped I/O**: An arrangement in which device registers appear at physical addresses, so a load or store to one goes to the device. [Chapter 1, section 1.5.1](01-operating-systems.md#151-device-registers)
