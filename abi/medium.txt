# The boot medium's layout (docs/design-storage.md, "The boot medium's table"), in
# 512-byte sectors, the one source of where each partition lies. A slot is a boot
# partition and a system partition: boot A with system A, boot B with system B. The
# master boot record at sector 0 names the boot-selection record's partition, boot A
# and boot B in its first three entries and the extended partition in its fourth. The
# extended partition holds four logical partitions, in medium order system A, system B,
# the vault's partition and the data partition, each behind an extended boot record
# 1 MiB before it (medium_NAME_ebr); the extended partition starts at system A's
# record. Each record's first entry names its logical partition, from the record's own
# sector, and its second names the next record, from the extended partition's start,
# spanning that record and its partition; the data partition's record names the data
# partition alone. No record follows the data partition's, so a reader reads exactly
# four. Every partition but the data partition has a fixed start and length; the data
# partition has a fixed start and runs from medium_data_sectors_min sectors to the
# medium's end, and the extended partition ends where it ends. Every boundary is a
# multiple of 2048 sectors (1 MiB), and each partition starts where the record or
# partition before it ends, so a slot's boot partition, its system partition and that
# partition's record take 512 MiB, and the vault's and the data partition's sectors
# follow the two slots. Every entry's status is mbr_status_inactive. A boot partition
# is one FAT32 volume (medium_boot_type), the firmware's; a system partition holds the
# slot's EROFS image and the vault's and the data partition's hold their own file
# systems, which no firmware reads, so all three take the type of a native partition
# (0x83). Inside each boot partition, the slot's bootable file starts
# medium_slot_boot_start sectors from the partition's first sector, so the QEMU harness
# finds it without parsing the slot (docs/design-platforms.md, "Slots and the
# boot-selection record"); the 4 MiB before it hold the FAT's boot sector, reserved
# area and tables, which a FAT32 of the whole partition with 1 KiB clusters fits
# (tools/lib/erx/pi_medium.rb).
#
# The record partition (docs/design-platforms.md, "Slots and the boot-selection
# record") is one FAT16 volume laid out in MiB regions, so that the reset count and the
# boot-selection record each have an erase unit of their own. Counted from the
# partition's first sector: MiB 0 holds the boot sector and the start of the reserved
# area; the reset count is the sector medium_record_count_start, the first of MiB 1,
# inside the reserved area, which no FAT reader reads; MiB 2 holds the end of the
# reserved area, both FATs and the root directory; and the record is the sector
# medium_record_select_start, the first of MiB 3, where the data area starts, the one
# 512-byte cluster of the volume's autoboot.txt. The data area fills the partition's
# last 5 MiB, 10,240 clusters of 512 bytes, which makes the volume a FAT16 by its
# cluster count. The partition starts 1 MiB into the medium, so it ends 9 MiB in, and
# boot A starts 12 MiB in. Firmware names a slot by its boot partition's number, its entry's
# index in the master boot record counted from 1: medium_slot_a_partition and
# medium_slot_b_partition. The record has exactly two encodings, medium_record_a while
# slot A is committed and medium_record_b while
# slot B is, each followed by zeros to the end of the sector; the two have the same
# length, since a commit rewrites the sector and never the FAT's directory entry that
# records the file's length. Each is the Raspberry Pi firmware's autoboot.txt naming
# the committed slot's partition, and the other slot's in its [tryboot] section;
# medium_record_a's text is, line by line, "[all]", "tryboot_a_b=1",
# "boot_partition=2", "[tryboot]", "boot_partition=3", each ended by a line feed, and
# medium_record_b's swaps the two numbers.
