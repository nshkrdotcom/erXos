# data: one erx_fs grant of /data's tree for each grantee, read-write and bound to the
# grantee's domain id. Each grantee mounts it at /data (docs/design-files.md, "A facet's
# mount"); the system domain's travels on the storage domain's system connection. Its max_request is files_max_frame_min (property 16), not the
# largest 9P msize, 65560, since a request is measured as its encoded Erlang term, which
# for a 64 KiB write with its envelope is longer than that; in_flight caps the requests the grant holds at once; max_heap_size, in
# words (2 MiB), bounds the grant's process, which holds up to in_flight write requests of
# 64 KiB with their data. reductions and period_ns bind no erx_fs grant. The storage
# domain takes two connections, root's session and one more while a session is replaced,
# and four more, one for each app of QEMU virt's apps row, whose template the build
# grants packages,
# and root's session four: data, net, and one more for each while its server is
# replaced; a domain's system connection counts against no quota (life_connections,
# liberx/system/dom_life.c). The network domain takes two, as the storage domain does for sessions,
# and four more, one for each app of QEMU virt's apps row, whose template the build
# grants net; the display domain, whose display no source facet grants, takes four,
# one for each app, whose template the build grants the display. Each board's machine
# record reckons its max_connections from these rows.
service data
  server @domain.storage
  interface files
facet data
  grantee system
  service @service.data
  operations none
  max_request 131072
  in_flight 16
  reductions 100000
  period_ns 1000000000
  max_heap_size 262144
facet data_session

  grantee @session.system
  service @service.data
  operations none
  max_request 131072
  in_flight 16
  reductions 100000
  period_ns 1000000000
  max_heap_size 262144
# home: the users' homes, the data volume's root/ and home/ directories, which the
# storage domain serves as a files service of its own; each grant reaches its grantee's
# own home alone. Its name is home_service (abi/manifest.txt), by which the build finds
# it: its facet rows, one for each session template but the app template, are among
# the rows the build derives (docs/design-files.md, "A user's home").
service home
  server @domain.storage
  interface files
# packages: the installed app packages, the data volume's packages/ directory, which the
# storage domain serves as a files service of its own; each grant reaches that directory
# alone (docs/design-packaging.md, "Where a package lies"). Its name is
# packages_service (abi/manifest.txt), by which the build finds it: its facet rows, the
# system domain's read-write and the app template's read-only, are among the rows the
# build derives from a board's apps row.
service packages
  server @domain.storage
  interface files
# system: the booted slot's system partition, the `system` tree, which the storage
# domain mounts once and serves as a files service of its own; its grants reach the
# partition's apps/ alone and every one refuses writes (docs/design-storage.md, "The
# `system` tree"). Its name is system_service (abi/manifest.txt), and its server holds
# the manifest's `system` window (property 19), as on every board this part serves. The
# mint starts only on a boot whose block service names the window.
service system
  server @domain.storage
  interface files

# display: the display domain's window tree (docs/design-display.md, "A display's
# session"), of the windows interface, and its display record. No facet grants it and no
# start row names it, so the display shows its empty layout's background. The policy is
# single and the idle times 0, which the display_domain suite boots
# (DisplayDomain.manifest); the domain library passes the idle times to the domain's
# environment, and nothing in the display domain reads them yet, so 0 has no meaning
# of its own here.
service display
  server @domain.display
  interface windows

  idle_dim_s 0
  idle_off_s 0
# log: the system log's write interface (docs/design-log.md, "The log facet"), served by

# No facet row grants it, so no other domain holds a log facet. A row that grants it

# "log facet").

  interface log

# inspect: the inspector's queries for each session made from root's template
# (docs/design-live.md, "The inspect service"), served by the system domain, so it
# travels on the session's system connection and takes none of max_connections. A
# request is a path and its options within 4 KiB; in_flight is the design's default of
# two query workers at once; max_heap_size, in words (512 KiB), bounds the facet's
# process, which holds the requests in flight, not the answers.

  server system
  interface inspect

  service @service.inspect
  operations none
  max_request 4096
  in_flight 2
  reductions 100000
  period_ns 1000000000
  max_heap_size 65536

# machine: the domain service's tree, /machine/ctl, through which a session asks for the

# session, ending with it and started with its principal, so it travels on the session's

# clock: the wall clock's one authority (docs/design-time.md, "The clock facet"), served
# by the system domain, where erx_clock_sup registers as its server (erx_facet:serve/2).
# root_clock grants each session made from root's template the set operation alone, so
# root sets the clock with date ("Setting the clock by hand") and sends
# no samples, the sample operation being ntpd's. A request is one small tuple within
# 256 bytes, and a set waits for one step, so one is in flight; max_heap_size, in words
# (64 KiB), bounds the facet's process, which holds only that request.
service clock
  server system
  interface clock

  name "clock"
  grantee @session.system
  service @service.clock
  operations set
  max_request 256
  in_flight 1
  reductions 100000
  period_ns 1000000000
  max_heap_size 8192
